### 迁移基线：v1 业务行为完整保留

迁移前先以 v1 源码、配置、数据格式、管理入口和运行日志建立行为清单。清单覆盖自动与手动入口、消息池和采集、召回、自动提取、Dream、画像、人设、记忆及来源数据、索引同步、错误与重试、任务状态、Web/API/命令管理能力，以及各引擎接入差异。每项行为都要标明 v1 的触发条件、输入范围、状态变化、持久化结果、失败处理和用户可见结果。

迁移实现按以下规则执行：

1. LivingMemory 继续拥有这些业务行为的定义、状态和结果；ChatLuna v2 负责提供适配所需的公共接口和运行时承载。
2. `agent`、`coding`、`character` 及后续引擎都必须接入同一套业务语义；引擎差异只能来自 v2 提供的实际输入、触发时机、上下文边界和注入位置，并由适配层显式表达。
3. 迁移阶段不得以“v2 已有实现”“接口较简单”或“实现成本较低”为理由删除 v1 行为。替代实现必须保持 v1 的可观察结果、数据关系和生命周期含义。
4. 方案中的“适配”“迁移”“重写”均仅表示承载方式变化。若讨论发现某项行为确实需要变化，先记录旧行为、新行为、原因、影响范围和验收条件，再单独确认。

### 调度与调用建议

1. **原生 memory 负责统一入口与分发。** 后端选择、新记忆写入和工作流调度采用一致的主后端解析结果；原生工具与管理操作通过 `ctx.memory` 访问当前后端。
2. **LivingMemory 负责自己的自动流程。** 自动召回、提取、提取后 Dream、画像更新和维护任务由插件协调器决定执行时机。原生默认后端继续使用原生自动流程。
3. **后端注册时声明自动流程归属。** 选择 LivingMemory 后，原生对应的自动触发入口让出调度职责。用户在后端配置中管理 LivingMemory 的窗口、间隔和自动任务开关。
4. **任务状态使用同一套业务记录。** 原生页面和专用页面读取 LivingMemory 自动任务的状态、取消结果和执行记录；自动提取继续由 LivingMemory 自己决定触发与消费时机。
5. **内部运行资源由插件服务持有。** 后端包装复用该隔离范围内的 LivingMemory 服务，消息池、任务队列和 Worker 随服务生命周期启停。

这组建议描述职责和行为。具体接口名称、参数类型和是否按工作流分别声明调度归属，在确认后细化。

### 任务状态与返回建议

| 契约部分 | 应表达的信息 |
| --- | --- |
| 目标 | 当前后端、预设、会话和调用来源，沿用已解析的作用域 |
| 自动提取输入 | LivingMemory 自有消息池、会话作用域、实际触发原因与消费游标 |
| Dream 输入 | 全量与提取后增量模式、触发原因，以及增量模式的目标记忆 ID |
| 取消 | 对应任务的取消信号、插件卸载时的终止与等待规则 |
| 提交结果 | 已受理任务的稳定 ID；沿用现有任务时返回该任务引用；条件不足时返回具体原因 |
| 执行结果 | 排队、运行与结束状态，以及统计、进度和错误信息；取消的结束状态在任务模型中明确 |

建议统一使用任务 ID 跟踪执行。页面收到受理结果后即可展示状态，最终结果由任务查询或订阅取得。LivingMemory 的任务记录作为执行状态依据，原生任务页面读取统一视图；一次执行在两个页面中对应同一个任务。任务存储与事件接口需要同步设计。

后端切换或卸载时，建议先停止旧后端接收新任务，再终止并等待其在途任务，最后释放 Worker 与数据库资源。显式选择的后端处于不可用状态时，保留选择并展示具体状态；就绪后恢复接入。

### 分池与消费归属建议

1. **消息池属于 LivingMemory 服务实例。** 实例内以框架解析的 `conversationKey` 和历史身份定位消息窗口。实例自身提供隔离边界，无需额外构造全局服务 ID。历史重置时更新运行期纪元，用于约束在途回填与消费。
2. **引擎名称和预设名称不进入原始消息池的分池键。** 同一会话、同一历史中的原始消息统一采集。群共享、按人隔离、自定义合并和 lane 均遵循解析后的会话键。
3. **消费者携带自己的记忆归属。** 提取游标、召回快照及任务记录关联池、实际预设和目标记忆作用域。提取游标在本次启用期间推进，每次切换预设重新建立起点。相同预设在不同群使用独立的消息池；长期记忆是否共享由记忆作用域决定。
4. **消息和任务保留接入时的归属。** 公共入口提供当时解析的会话、历史和记忆目标；回复关联原请求的归属。异步处理不能用后来变更的预设替换原目标。自定义会话合并多个路由时，逐条保留原来源与解析结果。
5. **旁听采集独立于活跃 Agent。** 公共接口需要在没有活跃 Agent 时提供会话归属和历史边界；具体首次建池与历史关联方式在 M05-C1 细化，采集无需启动引擎。

| 场景 | 建议行为 |
| --- | --- |
| 同一群采用 shared | 群内符合采集资格的消息进入同一会话池 |
| 同一群采用 personal，或使用不同 lane | 按各自 `conversationKey` 分池；实际回复按请求归属进入对应池 |
| 多个群使用同一预设 | 各群消息分别入池，消费者可按记忆作用域访问共享的长期记忆 |
| 同一会话仅切换引擎 | 保留消息池；实际预设和历史不变时沿用消费进度与召回快照，更新触发与注入接入 |
| 同一历史切换预设 | 原始消息池继续采集，消费者与快照切换到目标预设；提取计数归零，从本次切换的新起点累计消息 |
| 清空或重置当前对话 | 新历史使用新的消息窗口和消费边界，回填遵守重置界限；已形成的长期记忆通过独立管理操作删除 |
| 切换或分叉历史 | 读取目标历史可见范围；分支只继承分支点之前的消息，分支消费进度单独管理；继承历史的自动提取规则由 M06 确定 |

### 已确认：换预设后的提取范围

2026-11-03，用户选择“从切换后的消息开始”，并明确每次切换预设与重启统一重新计算提取阈值。同一会话的原始消息池保持连续，自动提取建立新的消费起点：

| 场景 | 自动提取范围 |
| --- | --- |
| A → B | B 的提取计数从 0 开始，只累计本次切换后属于 B 的消息；旧计数与待提取积压结束 |
| A → B → A | 切回 A 时再次从 0 开始，旧 A 和 B 期间的消息均不作为本次待提取积压 |
| 重启 | 提取计数从 0 开始；历史预热提供上下文，回填旧消息不计入新一轮阈值 |
| 原始采集 | 切换预设时继续使用同一采集机制和消息池，按消费归属筛选提取输入 |

实施草案：记录切换在入池顺序中的边界，并结合消息的实际预设与请求归属筛选。切换后的在途回复仍按原请求归属处理，异步处理完成时间不改变归属。接口字段与切换的生效时点在 M02-C1、M05-C2 细化。

本项确认自动提取的素材归属及重新计数规则，详见下文 M06。召回使用的聊天上下文范围和手动选择历史文本提取分别定义。

### 在途调用的 v1 核对结果

`clearAll()` 与 `clearByConversation()` 只删除提取状态；`drain()` 在下一块开始前发现状态对象已经失效后停止继续排干，已进入 `run()` 的模型调用不接收取消信号。调用返回后仍按启动时保存的作用域提交记忆、来源和 `onExtracted` 回调，随后旧状态对象的游标更新不会写入新状态。v1 测试 `tests/extraction-coordinator.spec.ts:848-881` 验证了清理期间旧批次完成、清理后的新消息由新状态接管。

v1 服务停止会停止 Dream、画像和向量索引，但提取协调器没有独立停止入口；消息日志在上下文 dispose 时释放。v2 已确认插件卸载时取消自动提取在途调用：先停止接收新任务并使旧状态失效，再向在途调用传递取消信号，等待任务收尾后释放消息池、存储和索引资源。会话清理与预设切换仍沿用 v1 语义，已开始的单次调用可以完成并提交原作用域；卸载取消不推进游标、不重试，也不允许尚未提交的结果在取消后落库。详见 [Agent Note：自动提取在途调用生命周期](../.agent/note/proposed/architecture/2026-11-04-extraction-inflight-lifecycle.md)。

### 已确认：切换预设与重启统一重新计数

每次切换预设或重启，都结束旧的阈值累计状态，建立新的自动提取消费起点。切回曾用过的预设时执行相同规则。先前“暂停积压、切回接续”的草案已撤销。

| 场景 | 行为 |
| --- | --- |
| A → B | B 的计数归零，从切换后的新消息累计；A 的旧计数与待提取积压失效 |
| A → B → A | A 再次从 0 开始，新的消息累计到阈值才触发提取 |
| 进程重启或插件重载 | 新建计数状态，历史回填不增加本次提取计数，也不恢复旧积压 |
| 原始消息池 | 切换预设时继续采集并保留配置窗口；重启后按历史能力预热；已有消息可用于上下文 |
| 同一预设用于其他会话 | 仅重置发生切换的会话；其他会话按自身状态运行 |

例如阈值为 10 条：A 已累计 7 条，切到 B 后为 0；B 又累计 4 条，再切回 A 仍为 0。重启后的计数同样为 0。

该决策确定重新计数与旧积压失效。会话清理与预设切换中的已运行模型调用沿用 v1 语义完成并写入原作用域；插件卸载中的调用按 M06-D4 取消。无论哪种情况，旧回调都不能推进或覆盖新一轮计数。

### 阈值与正常提取草案

建议沿用 v1 的窗口参数与分块算法，统一消息来源和每次启用的计数起点：

| 环节 | 建议行为 |
| --- | --- |
| 计数 | 使用本次启用起点及处理进度之后、归属当前消费范围的消息条数；用户消息与实际交付的助手回复均可计入，历史回填按 M06-D1 排除 |
| 阈值配置 | 保留 `extractionWindowMessages`，0 关闭自动提取；同一参数继续用于触发阈值与分块预算。v2 默认值待 M08-D1 确定 |
| 围绕完整交流提取 | 在实际回复完成后检查阈值，沿用 v1 的完整交流分段与附近聊天筛选；尚未闭合的末尾输入留待后续处理 |
| 旁听提取 | 消息入池后检查阈值，允许纯用户消息形成提取块；超长段沿用现有切分逻辑。该消费模式从统一消息池读取，跨引擎复用 |
| 分块 | 沿用 `planExtractionChunks` 的筛选、装包和交流边界；阈值决定开始处理的时机，实际一批的条数由分块结果决定 |
| 正常完成 | 有记忆时保存结果与来源后推进到该批末尾；模型有效返回“无可提取记忆”时，该批同样完成。期间新增的消息保留在处理进度之后 |

例如本批确定处理 10 条，执行期间又收到 3 条：本批成功完成后，待处理计数为 3。切换预设或重启则按已确认规则重新从 0 开始。实际分块仍以算法结果为准。

v1 的失败路径已核对：抛出异常时保留进度，连续 3 次后记失败并跳过；模型未配置、模型暂不可用及结构化结果解析失败会从 `run()` 正常返回，调用方随后推进进度。v2 按下节已确认的 M06-D2 区分这些结果并决定进度。

### 已确认：提取结果与失败处理

以下规则已于 2026-11-03 获用户确认，对应 M06-D2。进度表示这一批消息已处理到哪里；任务状态同时说明是否生成记忆、失败或跳过。具体接口与事务衔接继续细化。

| 结果 | 进度处理 | 任务与后续工作 |
| --- | --- | --- |
| 提取出记忆，记忆与来源成功提交 | 推进到本批末尾，执行期间新消息继续累计 | 记录完成及生成数量，后续流程使用已提交的记忆 ID |
| 模型返回通过结构及业务校验的空记忆列表 | 推进到本批末尾 | 记录完成、生成 0 条记忆 |
| 未配置模型或无法取得可用模型 | 保留当前进度 | 明确显示条件不足；不计为有效无记忆，也不增加模型执行失败次数；条件恢复后在后续正常触发时重新检查 |
| 模型请求失败、结构化结果不合法，或记忆与来源未成功提交 | 本次失败保留进度 | 记录具体失败阶段与原因；后续重试及达到上限后的处理见下文 |
| 记忆与来源已提交，随后索引同步或提取后回调失败 | 本批提取进度已完成 | 保留已提交的记忆 ID，单独记录索引或后续流程的失败；相应流程处理剩余工作，避免再次提取并重复写入记忆 |

失败处理沿用 v1 的基本节奏：本次失败结束当前处理，等下一次正常触发再尝试；达到失败次数上限后，记录失败及跳过的消息范围，再向后处理。达到上限后跳过的行为已确认，次数默认值留到 M08-D1。模型条件不足与执行失败分别处理。

v1 每次触发会重新读取未消费消息并分块。v2 重试期间在内存中保留失败批次的输入与上界，让失败次数及最终跳过范围始终对应这批消息；期间新增消息等待后续批次。该批次状态遵守已确认的切换与重启规则，旧计数及积压结束时一并释放。

索引同步与提取后工作分别报告执行结果。主数据提交失败时由提取流程记录失败；主数据已提交后，索引对账沿用其维护流程，Dream 等后续任务按自身任务状态处理。写入接口需明确传回已提交结果及后续错误，具体事务与任务衔接在 M03、M07 细化。

尚未取成批次的消息仍受 M05 的内存容量与淘汰规则约束。插件卸载时的自动提取调用按已确认的 M06-D4 直接取消；会话清理与预设切换仍允许已开始的调用完成并提交原作用域。旧任务回调始终只处理原计数状态。

### 输入、游标与切换边界草案

1. 同一池保留统一采集顺序，每次启用建立新的计数起点。消费者只统计新起点后符合归属与参与规则的消息，再计算阈值和切块。
2. 每个批次开始时确定消息集合、目标预设、本次计数状态、历史身份与读取上界。期间新入池的消息进入后续消费；切换后旧批次回调不能更新新状态。
3. 入口已解析的记忆目标与轮次实际使用的预设由 ChatLuna 公共接口关联。未唤醒引擎的旁听消息也要有明确归属；这一能力共用统一采集接口。积压请求遇到多次预设切换时的生效顺序，在 M02-C1 细化。
4. 发送较晚的回复关联原请求及原预设，不按发送时的最新配置重新归属。预设切换通知、接收记录与执行绑定需要提供可核对的顺序。
5. 一批提取的结果、来源和消费进度按同一目标处理；提取结果与失败处理遵循 M06-D2，插件卸载取消按 M06-D4 结束且不推进游标、不重试。启动时实时消息与回填的分界由 M05-D5 跟踪。
