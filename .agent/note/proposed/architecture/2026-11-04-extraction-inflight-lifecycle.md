# Agent Note: LivingMemory 自动提取在途调用生命周期

Status: proposed

## Problem

2026-11-06 消息来源调整见 [使用框架聊天历史](../../implemented/architecture/2026-11-06-framework-chat-history.md)。本文的原作用域结算与卸载取消规则继续适用；插件退出时释放消费状态和在途批次，框架聊天历史由框架管理，不随插件卸载删除。

自动提取由消息池触发，模型请求和记忆写入是异步操作。清空会话、切换预设、重启插件或卸载服务时，旧批次可能已经进入模型调用。若只删除消费状态，仍需要明确这次调用是否取消、结果是否可以提交、旧回调能否影响新计数状态，以及消息池和存储资源何时释放。

## Current v1 behavior

已核对 `src/service/workflows/extraction/coordinator.ts` 和 `tests/extraction-coordinator.spec.ts`：

1. `clearAll()`、`clearByConversation()` 只移除 `stateByScope` 中的消费状态，不向提取器传递 `AbortSignal`，也不取消已开始的模型调用。
2. `drain()` 在每个批次开始前比较 `stateByScope.get(key)` 与当前状态。状态被清除或替换后，当前 `drainNextChunk()` 返回后停止继续排干；正在执行的这一块可以完成。
3. 在途块完成后，提取结果和来源仍按启动时保存的 `scope` 提交，`onExtracted` 也使用原预设。旧状态对象随后不会写回新状态，因此不会推进新计数起点。
4. 会话清理先删除快照、清除召回和提取状态，再清空消息池；v1 测试确认清理期间旧请求只完成原批次，不消费清理后新纪元的消息。
5. v1 服务停止流程显式停止 Dream、画像和向量索引；提取协调器没有独立的 `stop()` 或统一取消入口。插件事件处理器会清理部分运行时状态，消息日志在上下文 dispose 时释放。

当前 v2 `MemoryBackend` 的 `extract(scope, messages)` 没有 `AbortSignal`，而 `dream(presetId, signal)` 已经有取消参数。M06-D4 已确认插件卸载时取消自动提取，因此需要扩展通用提取契约或由 LivingMemory 在更上层管理取消；不能把 Dream 的取消能力直接当作提取能力。

## Confirmed decision

2026-11-04：插件卸载时直接取消自动提取在途调用。卸载顺序为停止接收新任务、使旧状态失效、向在途调用传递取消信号、等待任务收尾，再释放消息池、存储和索引资源。取消不推进消费游标、不按普通提取失败重试，也不允许尚未提交的结果在取消后落库。

会话清理和预设切换保持 v1 的另一条语义：它们只使旧消费状态失效，已开始的单次模型调用可以完成并按原作用域提交；旧调用不能推进新计数状态或消费新纪元消息。若提交已经完成，卸载取消不回滚已提交的主数据，后续索引对账按其既有生命周期处理。

## Proposal

迁移时保留 v1 已验证的会话清理与状态隔离语义，并把生命周期契约显式化：

1. 清空会话、预设切换和新计数起点先使旧消费状态失效；旧批次不再继续排干，已开始的单次调用按 v1 语义完成或报告失败。插件卸载采用已确认的直接取消规则。
2. 旧调用的输入、目标预设、来源和任务引用在启动时冻结。调用完成后只允许提交到原作用域；不得更新新计数状态、重新使用新预设或消费新纪元消息。
3. ChatLuna v2 为插件卸载提供可等待的工作流生命周期接口。LivingMemory 在该接口上执行“停止接收新任务、停止排干、取消在途调用、等待任务收尾、释放消息池和存储资源”的顺序。
4. 卸载取消只作为生命周期适配行为；取消不写普通提取失败任务、不推进游标、不重试，模型已返回但尚未提交的结果不再落库。已完成的主数据提交不回滚。

## Alternatives considered

**在会话清理或预设切换时立即取消所有模型调用**：可以尽快释放资源，但会改变 v1 已开始批次仍可完成并提交的行为，也会改变失败任务和记忆写入结果；因此只在插件卸载时采用取消。

**清除状态但继续让旧调用更新新游标**：实现简单，但会让旧批次跨越切换或重置边界，造成新计数状态跳过消息或重复处理。

**卸载时完全忽略在途调用**：接近 v1 当前实现，但无法形成 v2 可验证的资源释放和服务停止契约，旧调用可能访问已停止的后端服务。

## Acceptance criteria

- 会话清理、预设切换和重启均能证明旧排干不再消费新计数起点之后的消息。
- 已开始的批次输入、原预设、来源和任务引用保持不变；其完成结果不会推进新状态，也不会按最新预设重新归属。
- 插件卸载会取消在途调用并等待收尾；取消不会推进游标、重试或写入尚未提交的结果，主数据已提交时不回滚。
- 会话清理和预设切换继续允许当前在途块按原作用域完成；不会因为旧回调重复提取或推进新状态。
- 插件卸载能按 v2 生命周期契约等待或取消在途任务，并在释放消息池、数据库、向量索引和模型资源前完成规定的收尾。
- v1 相关回归测试覆盖“请求等待期间清理会话”“新纪元消息由新状态接管”和“旧回调不改变新计数”三个边界。

## Risks

- v1 允许已开始调用继续提交；若会话清理同时意味着用户要求删除相关数据，仍需定义在途结果与清理操作的先后关系。
- 不同 v2 引擎和模型实现对取消的支持程度可能不同，不能把 `AbortSignal` 是否触发当成模型调用已经停止的证明。
- 旧调用提交到原作用域是有意保留的兼容行为，但在插件卸载期间必须由资源生命周期保证写入服务仍然有效。
