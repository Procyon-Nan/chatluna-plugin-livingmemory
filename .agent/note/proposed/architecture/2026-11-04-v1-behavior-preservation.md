# Agent Note: LivingMemory v1 业务行为保留基线

Status: proposed

## Problem

LivingMemory 从 v1 迁移到 ChatLuna v2 时，需要同时适配 v2 的插件接口、服务生命周期、消息接入、会话作用域和模型调用。若以 v2 现有的 memory 流程或某一个对话引擎为实现起点，容易把 v1 中已经存在的业务行为误当成可选能力，造成消息采集、召回、自动提取、Dream、画像、人设、数据管理或管理入口的语义丢失。

## Proposal

将 v1 的全部原本业务行为作为迁移基线。迁移的目标是保持 v1 的可观察业务语义，只改变实现所依赖的承载环境：

1. LivingMemory 继续拥有业务规则、状态、数据关系和结果定义，包括消息池与采集、召回、自动提取、Dream、画像、人设、记忆及来源、索引同步、任务状态、错误处理、重试和管理能力。
2. ChatLuna v2 负责提供公共接口和运行时适配，包括插件装配、服务生命周期、消息与历史输入、会话和作用域、模型调用、任务承载以及各引擎的接入点。v2 原生 `memory` 后端作为统一入口，LivingMemory 实现实际业务流程。
3. `agent`、`coding`、`character` 和后续引擎共用 LivingMemory 的业务实现。引擎差异由适配层传递实际触发时机、消息参与状态、上下文边界和注入位置，不复制或删减业务流程。
4. 迁移前建立 v1 行为清单。每项行为记录触发条件、输入范围、状态变化、持久化结果、失败处理和用户可见结果，并关联 v1 源码入口、v2 适配接口和迁移验收项。
5. v2 现有接口无法表达 v1 行为时，优先在 ChatLuna v2 增加具有通用意义的接口或扩展契约。只有确需改变业务语义时，才新建独立决策记录，写明旧行为、新行为、原因、影响范围和验收条件。

该基线不提前确定 v2 的默认配置数值；默认值继续由迁移方案 M08-D1 集中处理。它也不替代各专题对作用域、消息池、提取在途调用、数据导入和管理界面的具体契约。

## Alternatives considered

**直接套用 v2 原生 memory 流程**：可以减少初期适配代码，但会把原生 observer 窗口、原生调度和单一后端接口当成业务定义，无法完整承载 v1 的消息池、跨引擎采集、工作流、Dream、画像和管理行为。

**只迁移核心记忆读写**：实现范围较小，但会删除 v1 的召回上下文、自动提取、Dream、画像、人设、来源与任务管理等既有能力，无法满足兼容迁移目标。

**在迁移阶段重新设计业务行为**：可以获得一套新的 v2 业务模型，但会把接口适配与产品语义变化混在一起，无法判断差异来自 v2 承载还是主动改动，也无法验证旧数据和旧配置的兼容性。

## Acceptance criteria

- v1 行为清单覆盖源码、配置、数据、任务、管理入口和各引擎接入；每项都有 v2 适配位置和验收条件。
- 已有记忆、来源、画像、人设、Dream、召回、自动提取、消息池、索引同步、任务状态、错误与重试等行为在迁移方案中均有对应工作项，不因 v2 原生能力缺失而被静默删除。
- `agent`、`coding`、`character` 等引擎通过公共适配契约使用同一套 LivingMemory 业务流程，并保留 v1 对各引擎输入和触发差异的处理。
- v2 接口扩展能够表达未被现有接口覆盖的 v1 行为；扩展契约记录行为归属、生命周期、作用域和错误语义。
- 任一业务行为发生有意变化时，都有独立决策记录和针对旧行为、新行为及迁移影响的验收证据。
- v1 旧数据导入后，记忆、来源、画像及相关关系能够继续参与现有业务流程；导入范围和映射差异由 M03 明确记录。

## Risks

- v1 行为分散在多个插件、服务、工作流、RPC 和前端入口中，清单建立不完整会造成遗漏；实施前必须按源码入口和运行路径逐项核对。
- v2 接口扩展可能影响 ChatLuna 的其他 memory 后端，需要将通用契约与 LivingMemory 专用能力分开，并为公共变更补充框架侧验收。
- 维持 v1 语义会保留其部分复杂的状态和生命周期边界；应先建立兼容适配层，再根据真实运行和验收证据决定是否另行优化。
- v1 行为与 v2 平台约束冲突时，未经独立决策就直接选择平台默认行为，会形成未记录的语义变化。
