# M05：消息池维护方案

设计状态：**草案**。实施状态：**S3 采集层已落地，S6.5 改为拉取 `chat_observer`**。验收状态：**待真实宿主验证**。

更新日期：2026-11-03。总进度见 [迁移方案](migration-plan.md)。

## 已确认的边界

- LivingMemory 继续维护自己的消息池，作为召回和提取的输入。
- 统一消息采集是消息池设计的核心要求。`agent`、`coding`、`character` 等引擎共用一套采集、规范化、入池和读取机制；引擎差异放在触发、消费时机和记忆注入等执行接入处。
- ChatLuna v2 可以提供迁移所需的通用消息、历史和会话生命周期接口。
- 消息池及运行时消费游标采用内存管理；本次迁移不要求重启后恢复未完成提取，也不增加待消费消息与游标的持久化、重放机制。
- 切换预设时原始消息池保持连续，提取阈值与重启一样从 0 重新累计；切回原预设也重新开始，旧计数与待提取积压失效，见 M02-D2、M06-D1。

统一采集、内存生命周期边界及切换与重启重新计数已于 2026-11-03 确认。具体作用域键、入口契约、启动时实时消息与回填的边界、容量与历史切换规则继续讨论。

## v1 现状

| 项目 | 当前实现 |
| --- | --- |
| 所有者 | `ChatLunaLivingMemoryService` 持有 `MessageLogRegistry`；注册表按 `conversationId` 管理日志 |
| 存储 | 内存滚动日志，每会话容量 500 条；日志、去重键和提取游标随进程生命周期存在 |
| 普通对话 | `before-chat` 写入用户请求，`after-chat` 补入用户与回复文本；注册时提供会话绑定，使用实时输入建立消息池 |
| Character | 平台采集器持续记录符合接收范围的用户消息；`after-chat` 补入实际发出的回复；注册时额外提供 bot，用于平台历史回填 |
| 历史预热 | Character 冷启动回填目标为 200 条；适配器提供的分页决定实际取得的数量；缺少历史能力时从实时消息开始 |
| 顺序与去重 | 入池分配单调递增 `seq`；优先按消息 ID 去重，缺少 ID 时按用户、时间、内容组合去重；淘汰条目时同时移除对应去重键 |
| 回填与实时并发 | 回填期间实时消息进入临时缓冲；回填完成后先写历史，再写缓冲；重复项保留实时版本 |
| 回填失败 | 保留缓冲与未就绪状态，下次预热重试 |
| 召回读取 | 定位当前触发消息，读取它之前的历史窗口；定位失败时当前实现读取最近窗口 |
| 提取读取 | 每个预设与会话维护自己的游标；普通对话按完整交流片段取块，开启旁听提取时可以消费旁听消息 |
| 提取结果 | 单块处理正常返回后推进游标；抛出异常时保留游标，连续 3 次异常后记录失败任务并跳过该块；跳过及解析失败等正常返回分支的迁移语义在 M06 细化 |
| 清理 | 清空日志推进时间纪元并保留序号计数；释放注册表清除内存池；记忆的来源文本另行保存在记忆数据中 |

500 条约束针对单个已落池日志。当前注册表的会话数量、回填临时缓冲和未消费消息保留量由上述逻辑决定；持续积压时，容量淘汰会移除尚未提取的旧消息。普通对话与 Character 的历史预热能力取决于各自接入提供的历史来源。v2 迁移将这两类采集接入统一到公共消息入口。

## v2 统一入口的源码现状

- `chat/core/src/plugins/wiring.ts` 在激活决策返回 `ignore` 时结束本次分发；`chat/core/src/service.ts` 在接纳输入后发出 `chat/receive`。仅订阅 `chat/receive` 无法取得未触发对话的旁听消息。
- `chat/observer/src/service.ts` 已通过公共 `message`、`middleware`、`send` 事件观察消息，通过 `chat/receive` 标记进入对话的消息，并接入 Agent 请求与 ingest。这些入口为各引擎共用。
- `chat/core/src/session.ts` 的发送事件携带成功发送的消息 ID 和来源分类；具体执行归属与历史分支关联还需要在公共契约中补齐。

以上路径均位于 `packages/`。建议以现有公共接入和 observer 为基础，提供 LivingMemory 可订阅的规范化消息接口。接口需要覆盖旁听、实际交付和 Web/API 入口；具体事件名称、字段及接入位置继续细化。

**实施结果（S6.5）**：观察层没有「消息已入池」的公共事件，因此采集改为拉取式——`MessageCollector.sync` 在会话钩子里调用 `recentOfConversation` 读取通道缓冲，按消息号去重后入池；机器人自身的 `self` 回声跳过，回复由 `recordReplies` 从 `agent.session.messages()` 记录一次。观察层的回填不写入 `observed` 缓冲，召回窗口因此由 `recallWindow` 在池内不足时用会话历史补足（`transcript/message_log/session_history.ts`）。仍待框架侧补充的只有推送事件，用于旁听消息在没有任何后续轮次时也能入池。

## v2 维护草案

### 1. 统一采集与分池

建议采用以下职责划分：ChatLuna 的公共消息接入提供来源、会话绑定和实际交付记录；LivingMemory 通过一个采集模块维护注册表、消息日志及消费游标。平台和 Web/API 的输入差异在公共入口归一化，LivingMemory 各引擎接入复用同一套入池逻辑。

采集按配置的会话和消息范围持续进行。引擎是否回复、是否触发召回、是否允许旁听提取，由对应执行阶段和消费配置决定。后续收到引擎采用消息的通知时，关联已有记录的请求或轮次即可。引擎接入负责传递触发信息、读取所需窗口和注入记忆。

统一采集可以复用 v2 已有的观察与消息规范化能力；具体实现归属以公共接口是否满足上述契约为依据。LivingMemory 的消息窗口和消费进度由自身工作流管理。

建议在每个 LivingMemory 服务实例内，以 `conversationKey` 和当前历史身份识别一份消息池；实例提供服务隔离，运行期纪元用于约束重置前的在途工作。作用域采用 v2 解析结果，覆盖群聊、私聊、按用户隔离、自定义会话键及 lane。具体划分与场景见 [迁移方案 M02](migration-plan.md)。

同一个对话的消息可以供召回、提取等消费者读取；消费者分别持有游标或读取边界。引擎名称作为执行元数据，池的分合遵循会话身份与历史边界。同一会话仅变更引擎时继续使用同一采集机制；是否发生历史切换按显式会话操作判定。

预设归属记录在消费者、任务和消息的接入信息中。换预设时原始采集保持连续，提取计数归零并建立新消费起点，召回快照按目标预设管理；切回曾用预设时执行同样的重新计数规则，见 [迁移方案 M06](migration-plan.md)。没有活跃 Agent 时也应能取得会话归属并采集消息。

### 2. 消息来源与入池资格

| 输入 | 入池与消费建议 |
| --- | --- |
| 用户发给当前对话的消息 | 记录稳定消息身份、用户身份、内容、时间和作用域；在被引擎采用时关联对应请求或轮次 |
| 符合采集范围、未触发引擎回复的群消息 | 经同一入口持续进入所属消息池，记录参与状态；旁听提取是否开启由 LivingMemory 配置决定 |
| 助手回复 | 以对用户成功交付的消息为依据，关联原始请求、具体 session 和实际消息 ID；分句、分段发送按实际记录归档 |
| 历史回填 | 使用与实时相同的规范化格式，并保留来源、历史边界和原始消息身份 |
| Web/API 等入口 | 通过 v2 公共输入及交付接口进入同一采集模块，使用入口提供的稳定 ID |

入池资格还需表达普通聊天、命令、交互确认、内部任务及自身回声等来源类别。系统提示、工具执行轨迹和推理文本由其原有系统管理；LivingMemory 消费对用户可见且符合采集规则的消息。

用户消息先被观察、随后又被引擎采用时，应关联或更新同一条记录的参与状态。助手生成、实际发送与平台回声也应通过关联 ID 对应到同一组已交付消息。

### 3. 顺序与去重

- 同一池按入口接收顺序串行提交，归一化中的昵称、图片等异步处理保持这个顺序。
- 为最终收录的消息分配递增 `seq`，通过 `seq` 表达消费进度；平台时间用于展示和历史排序。
- 平台消息的去重身份包含平台、账号或来源路由、频道和原始消息 ID，覆盖自定义会话合并多个来源的情况。
- 对平台、Web/API 及投递事件建立可对应的稳定身份，回填与实时共享同一去重规则。
- 缺少平台 ID 的输入沿用既有组合身份，或使用入口生成的稳定内部 ID；具体规则按入口契约确定。
- 消息编辑、撤回和重发的更新语义在事件契约中单独定义；已在执行的任务持有确定的输入范围。

### 4. 回填与读取边界

建议延续“先接住实时消息，再完成历史预热”的顺序：

1. 创建池并记录作用域、当前历史纪元与首条实时消息边界。
2. 发起历史读取，期间持续接收实时消息到有序缓冲。
3. 根据当前会话可见范围及重置边界筛选历史，与实时记录去重。
4. 按历史顺序提交回填，再提交实时缓冲，标记预热完成。
5. 历史来源能力与错误显式反映在池状态中；失败重试期间保持实时缓冲的归属和顺序。

ChatLuna 侧需提供按会话读取可见历史的能力，并明确平台历史和 session 历史的覆盖范围。平台历史包含所在频道的消息，按用户隔离或自定义会话必须先按原会话采集规则筛选。

召回读取固定在触发消息之前的窗口；提取读取自己的未消费区间，并在任务启动时锁定本批的上界。两者异步执行期间继续接收新消息，后续消息进入下一次消费。

正常提取完成时，按已确认的 M06-D2 只推进到本批已处理的边界，期间新增消息继续累计。失败重试固定本批输入与上界，达到失败次数上限后记录并跳过；主数据提交后的索引或后续任务失败分别处理。切换预设和重启按 M06-D1 重新计数。阈值配置与分块草案见 [迁移方案 M06](migration-plan.md)；默认值留到 M08-D1 集中确定。

提取消费可以选择完整交流片段或旁听窗口，两者读取同一消息池，通过参与状态和消费规则选择内容。回填用于提供历史上下文，旧消息不计入新的提取阈值，也不作为待恢复的积压；启动期间实时接收的消息按新起点累计。

按本次消费起点、预设归属和参与状态筛选后，再计算阈值与切块。切回预设时建立新起点，旧消息保留其上下文用途，旧计数及待提取积压结束。

### 5. 清空、切换与生命周期

| 操作 | 建议处理 |
| --- | --- |
| 显式重置或清空对话 | 建立新纪元，清理当前池与消费状态，使旧回填和在途结果受旧纪元约束；新消息进入新纪元 |
| 切换历史 session | 切换到目标历史对应的池与消费状态，根据目标历史预热 |
| 从历史分支继续 | 按分支点定义可见历史和初始消费边界，父分支后续消息保留在原分支 |
| 同一历史仅切换引擎 | 消息池继续接收；预设与记忆作用域不变时沿用消费进度，调整引擎的触发与注入接入 |
| Agent 实例释放后重新打开 | 按同一会话与历史身份接续池；显式会话操作决定历史边界 |
| 变更预设 | 原始池保持连续，按 M02-D2、M06-D1 将提取计数归零，从本次切换后的新消息累计；切回原预设也重新开始 |
| 变更后端 | 停止旧后端的消费任务，按新绑定建立消费关系；遵循 M01 后端生命周期契约 |
| 插件停止 | 停止采集入口，终止并等待回填和消费任务，然后释放消息池、运行时消费游标与其他资源 |

闲置池回收、回填缓冲上限和未消费积压处理继续讨论。v1 每会话容量为 500 条；v2 容量与淘汰策略在 M05 确认，默认容量数值留到 M08-D1 集中确定。

### 6. 内存生命周期与冷启动

已确认采用内存消息池。消息日志、去重集合和运行时消费游标随插件服务生命周期存在。进程重启或插件重载后创建新池，从可用历史预热；提取计数从 0 开始，采用与切换预设相同的重新计数规则，旧计数与待提取积压结束。

历史预热与实时采集使用同一规范化与去重规则，其覆盖范围取决于历史接口。已形成记忆及其来源文本按业务数据独立持久化。

本次迁移不实现待提取消息和消费游标落库、跨重启接续任务或中断重放。任务记录的展示与结束状态仍由 M01 管理。容量、运行期间的积压淘汰、闲置回收及启动时实时消息与回填的边界保持为待讨论项。
